# On-box performance analysis (T1.8)

Generated by `bench/run_analysis.py` on the machine described below. Read the
two kinds of number here differently.

**MEASURED** — observed on this machine, by a clock:

- Kernel wall-clock times, from CUDA events (medians of repeated launches).
- Per-kernel durations and launch counts, read back from the nsys traces.
- Kernel resource footprints (registers/thread, shared memory/block) reported
  by `cudaFuncGetAttributes`.

**MODELED** — arithmetic derived from those times plus the shapes, not observed:

- TFLOP/s and GB/s, computed as analytic FLOP and byte counts divided by the
  measured time. They assume the kernel moves exactly the bytes the model says;
  real traffic including cache behaviour is not visible without counters.
- '% of peak' columns, which additionally assume a peak this card never
  advertises directly (see the compute-peak note below).
- Theoretical occupancy, from `cudaOccupancyMaxActiveBlocksPerMultiprocessor`.
  It is an upper bound the hardware permits, **not** achieved occupancy.

**NOT AVAILABLE HERE** — every counter-derived quantity. This machine denies
access to GPU performance counters (`ERR_NVGPUCTRPERM`, confirmed by smoke test;
it is a container, and the restriction is a per-host driver property that cannot
be lifted from inside). So SM and memory speed-of-light, **achieved** occupancy,
**measured** DRAM throughput and shared-memory bank-conflict counts are absent
rather than estimated. They are produced by `bench/profile_ncu.sh` on a
counter-capable RTX 3090 and land in [summary.md](summary.md), which is tracked
as open work (T1.9b) against a docs-only release. Until then, every claim in
this file about *which unit saturates* is a model, and is labelled as one.

**Which compute peak, and why.** The roofline below uses the fp32 FMA peak
(`SMs x 128 lanes x 2 flops x boost clock`), not the 71 TFLOP/s fp16 tensor-core
peak. Every multiply in these kernels is an `FFMA` on the CUDA cores: the contract
is fp32 accumulation, and the halves are converted once when a tile is staged, so
the tensor cores are never issued to. Comparing against a peak the kernel cannot
reach by construction would understate it; the tensor-core gap is a design
difference and is discussed against flash-attn in [../benchmarks.md](../benchmarks.md).

Prefill is shared-memory limited, not register limited: 41,472 B per block against
the 100 KB an SM can distribute allows
2 blocks, while the register file would allow more. Decode reaches full theoretical
occupancy per SM — its problem is having enough blocks to hand out, which is what
the split study below addresses.

## Prefill roofline

`FLOPs = 4 B H N^2 d` (halved for causal); `bytes = (3 reads + 1 write) B H N d 2`.

| shape | ms | TFLOP/s | % of fp32 peak | GB/s | % of DRAM peak |
| :-- | ---: | ---: | ---: | ---: | ---: |
| B=4, H=12, N=2048, causal | 2.321 | 11.10 | 30.7% | 21.7 | 2.3% |
| B=8, H=12, N=4096, causal | 17.428 | 11.83 | 32.7% | 11.6 | 1.2% |
| B=8, H=12, N=4096, full | 33.529 | 12.30 | 34.0% | 6.0 | 0.6% |
| B=1, H=12, N=1024, causal | 0.224 | 7.19 | 19.9% | 28.1 | 3.0% |

Prefill sits at a third of the fp32 compute peak and a few percent of the DRAM
peak, so it is compute-side bound — but not by the FMA pipe itself. The QK loop
reads 32 bytes of shared memory per 16 FMAs and the PV loop 48 bytes per 32, about
1.75 bytes per FMA, while an SM sustains 128 B/cycle of shared memory against 128
FMA/cycle. That ratio caps this blocking near 57% of fp32 peak before staging,
softmax bookkeeping and the three barriers per tile are paid for. Confirming that
shared memory is the limiter needs counters, and is a stated goal of T1.9.

## Decode roofline and the split-size study

`FLOPs = 4 B H S d` per step; `bytes = 2 B H S d 2` for the cache plus the
split workspace written by pass 1 and read by pass 2.

Chunk selection targets `2 x SM count = 164` blocks: the largest
power-of-two chunk in [128, 1024] that reaches it, falling back to 128 when no
chunk does.

### Before / after: fixed Sk=512 versus adaptive

| shape | Sk before | blocks | ms | GB/s | Sk after | blocks | ms | GB/s | speedup |
| :-- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| B=1, H=12, S=512 | 512 | 12 | 0.0537 | 29.4 | 128 | 48 | 0.0174 | 91.6 | 3.08x |
| B=1, H=12, S=1024 | 512 | 24 | 0.0505 | 62.5 | 128 | 96 | 0.0178 | 179.7 | 2.84x |
| B=1, H=12, S=2048 | 512 | 48 | 0.0898 | 70.3 | 128 | 192 | 0.0302 | 211.9 | 2.98x |

| shape | chunk | blocks | ms | GB/s | % of DRAM peak | TFLOP/s | % of fp32 peak |
| :-- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| B=1, H=12, S=512 | 128 | 48 | 0.0170 | 94.2 | 10.1% | 0.093 | 0.26% |
| B=1, H=12, S=1024 | 128 | 96 | 0.0174 | 184.0 | 19.7% | 0.181 | 0.50% |
| B=1, H=12, S=2048 | 128 | 192 | 0.0301 | 212.1 | 22.7% | 0.209 | 0.58% |
| B=1, H=12, S=4096 | 256 | 192 | 0.0582 | 218.0 | 23.3% | 0.216 | 0.60% |
| B=8, H=12, S=2048 | 1024 | 192 | 0.1987 | 253.8 | 27.1% | 0.253 | 0.70% |

Decode does two FLOPs per byte of cache read, so it is a bandwidth problem with no
arithmetic to hide behind — the compute column is there to show how far from
compute-bound it is. What limits it at small batch is neither bandwidth nor the
access pattern (one warp reads one cached row as a single 128-byte coalesced
request) but the number of blocks in flight.

### What the decode comparison baseline is, and is not

The decode line in [../benchmarks.md](../benchmarks.md) is measured against a
**per-step eager SDPA loop**: one `scaled_dot_product_attention` call per decoded
token, over the whole cache, with a single-row query. That is the obvious way to
decode in PyTorch and it is a correct reference, but it is not a decode-optimised
kernel — it does not split the KV dimension, so it leaves unused exactly the
parallelism that the fixed-chunk version of this kernel used to leave unused. Beating
it is a low bar and should be read as such.

The serious baselines are **flash-attn's dedicated decode path**
(`flash_attn_with_kvcache`) and **FlashDecoding**, both of which split the KV
dimension the way this kernel does and additionally run the arithmetic on tensor
cores. Benchmarking against those is deferred; until it happens, no claim is made
here about how this kernel compares to a state-of-the-art decode implementation.

## Timeline observations (nsys)

Read back from `prefill.nsys-rep` and `decode.nsys-rep` in this directory,
collected with `nsys profile -t cuda` (no `--gpu-metrics-device`, which is
counter-gated). These are wall-clock kernel durations from the trace, not
counter measurements.

| trace | kernel | launches | mean us | median us | min us | max us | spread (sd/mean) |
| :-- | :-- | ---: | ---: | ---: | ---: | ---: | ---: |
| prefill | `prefill_kernel<(bool)1>` | 25 | 2138.69 | 2011.47 | 1957.97 | 2385.43 | 8.2% |
| decode | `decode_split_kernel` | 25 | 13.45 | 13.44 | 13.41 | 13.82 | 0.6% |
| decode | `decode_merge_kernel` | 25 | 2.45 | 2.43 | 2.43 | 2.56 | 1.2% |

- Prefill is one kernel per call: `prefill_kernel<(bool)1>` accounts for 99.8% of GPU time across 25 launches, with 8.2% run-to-run spread.
- Decode is two kernels per call. The merge pass costs 2.45 us against the split pass's 13.45 us, so it is 15.4% of the call at the chunk size the selection rule picked for this shape (B=1, H=12, S=1024). That fraction is the price paid for parallelism, and it grows as the chunk shrinks — which is why the rule prefers the largest chunk that still fills the device rather than the finest split available.
