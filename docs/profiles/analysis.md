# On-box performance analysis (T1.8)

Generated by `bench/run_analysis.py`. Every figure here comes from CUDA-event
timings, the CUDA occupancy API, or `cudaFuncGetAttributes` — **this machine has
no access to GPU performance counters**, so nothing below is a profiler
measurement. SM/memory speed-of-light, achieved occupancy, measured DRAM
throughput and bank-conflict counts require Nsight Compute and are produced
separately on a counter-capable card by `bench/profile_ncu.sh` (T1.9), landing in
[summary.md](summary.md). Those numbers are deliberately absent here rather than
estimated.

**Which compute peak, and why.** The roofline below uses the fp32 FMA peak
(`SMs x 128 lanes x 2 flops x boost clock`), not the 71 TFLOP/s fp16 tensor-core
peak. Every multiply in these kernels is an `FFMA` on the CUDA cores: the contract
is fp32 accumulation, and the halves are converted once when a tile is staged, so
the tensor cores are never issued to. Comparing against a peak the kernel cannot
reach by construction would understate it; the tensor-core gap is a design
difference and is discussed against flash-attn in [../benchmarks.md](../benchmarks.md).

Prefill is shared-memory limited, not register limited: 41,472 B per block against
the 100 KB an SM can distribute allows
2 blocks, while the register file would allow more. Decode reaches full theoretical
occupancy per SM — its problem is having enough blocks to hand out, which is what
the split study below addresses.

## Prefill roofline

`FLOPs = 4 B H N^2 d` (halved for causal); `bytes = (3 reads + 1 write) B H N d 2`.

| shape | ms | TFLOP/s | % of fp32 peak | GB/s | % of DRAM peak |
| :-- | ---: | ---: | ---: | ---: | ---: |
| B=4, H=12, N=2048, causal | 2.001 | 12.88 | 34.9% | 25.1 | 2.7% |
| B=8, H=12, N=4096, causal | 14.960 | 13.78 | 37.4% | 13.5 | 1.4% |
| B=8, H=12, N=4096, full | 29.003 | 14.22 | 38.6% | 6.9 | 0.7% |
| B=1, H=12, N=1024, causal | 0.193 | 8.33 | 22.6% | 32.5 | 3.5% |

Prefill sits at a third of the fp32 compute peak and a few percent of the DRAM
peak, so it is compute-side bound — but not by the FMA pipe itself. The QK loop
reads 32 bytes of shared memory per 16 FMAs and the PV loop 48 bytes per 32, about
1.75 bytes per FMA, while an SM sustains 128 B/cycle of shared memory against 128
FMA/cycle. That ratio caps this blocking near 57% of fp32 peak before staging,
softmax bookkeeping and the three barriers per tile are paid for. Confirming that
shared memory is the limiter needs counters, and is a stated goal of T1.9.

## Decode roofline and the split-size study

`FLOPs = 4 B H S d` per step; `bytes = 2 B H S d 2` for the cache plus the
split workspace written by pass 1 and read by pass 2.

Chunk selection targets `2 x SM count = 164` blocks: the largest
power-of-two chunk in [128, 1024] that reaches it, falling back to 128 when no
chunk does.

Decode does two FLOPs per byte of cache read, so it is a bandwidth problem with no
arithmetic to hide behind — the compute column is there to show how far from
compute-bound it is. What limits it at small batch is neither bandwidth nor the
access pattern (one warp reads one cached row as a single 128-byte coalesced
request) but the number of blocks in flight.

### What the decode comparison baseline is, and is not

The decode line in [../benchmarks.md](../benchmarks.md) is measured against a
**per-step eager SDPA loop**: one `scaled_dot_product_attention` call per decoded
token, over the whole cache, with a single-row query. That is the obvious way to
decode in PyTorch and it is a correct reference, but it is not a decode-optimised
kernel — it does not split the KV dimension, so it leaves unused exactly the
parallelism that the fixed-chunk version of this kernel used to leave unused. Beating
it is a low bar and should be read as such.

The serious baselines are **flash-attn's dedicated decode path**
(`flash_attn_with_kvcache`) and **FlashDecoding**, both of which split the KV
dimension the way this kernel does and additionally run the arithmetic on tensor
cores. Benchmarking against those is deferred; until it happens, no claim is made
here about how this kernel compares to a state-of-the-art decode implementation.

## Timeline observations (nsys)

From `prefill.nsys-rep` and `decode.nsys-rep` in this directory, collected with
`nsys profile -t cuda` (no `--gpu-metrics-device`, which is counter-gated):

- Prefill is a single kernel per call with no host-side gap between iterations;
  25 launches vary by 0.9%, so the measurement is stable and there is no
  launch-overhead surprise to chase.
- Decode is two kernels per call. The merge pass is ~4.5% of the call at Sk=512
  and grows as the chunk shrinks, which is the cost the selection rule is trading
  against parallelism — it prefers the largest chunk that still fills the device
  rather than the finest split available.
- No unexpected memcpys appear between launches: the workspace comes from the
  caching allocator and stays on device.
