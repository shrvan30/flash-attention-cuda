# Nsight Compute profiles (T1.9b) — open, tracked against v2.0.1

This file is generated by `bench/profile_ncu.sh` on a counter-capable RTX 3090 and is
**not yet populated**. It is the one deliberate gap in the v2.0.0 release, and it is
recorded here rather than quietly omitted.

## Why it is empty

GPU performance-counter access is a **per-host driver property**. The machine every
published number in this repository was measured on denies it: every `ncu` invocation
returns `ERR_NVGPUCTRPERM`, confirmed by smoke test, as root, and with
`--target-processes all`. That machine is an unprivileged container, and the standard fix

```
options nvidia NVreg_RestrictProfilingToAdminUsers=0
```

requires reloading the kernel module and rebooting the host, which a container cannot do.
So the counter-derived figures — SM speed-of-light, memory speed-of-light, **achieved**
occupancy, **measured** DRAM throughput and shared-memory bank-conflict counts — are
absent rather than estimated.

## What exists instead

[analysis.md](analysis.md) holds everything that *was* measurable, and separates it
honestly into what was observed and what was derived:

- **Measured**: kernel wall-clock times from CUDA events, per-kernel durations and launch
  counts read back from nsys traces, and register/shared-memory footprints from
  `cudaFuncGetAttributes`.
- **Modeled**: TFLOP/s, GB/s and every "% of peak" column — analytic FLOP and byte counts
  divided by measured time — plus **theoretical** occupancy from the CUDA occupancy API,
  which is an upper bound the hardware permits and not what the kernels achieve.

The distinction matters most for the central performance claim. `analysis.md` argues that
prefill is limited by shared-memory bandwidth rather than the FMA pipe, from an operand
ratio of roughly 1.75 bytes per FMA against an SM that sustains about 1.0. That argument
is a **model**. Confirming which unit actually saturates is exactly what this file is for.

## What to run, and where

On a counter-capable RTX 3090 — same GPU model as the published benchmarks, so the
profiles line up with them — at the `v2.0.0` commit:

```bash
git clone https://github.com/shrvan30/flash-attention-cuda.git
cd flash-attention-cuda && git checkout v2.0.0
pip install -e .
python -m pytest -m gpu          # same-arch sanity check
bash bench/profile_ncu.sh
```

The script captures `ncu --set full` on prefill (N=2048, causal, B=4, H=12) and decode
(S=1024), writes `ncu_prefill.ncu-rep` and `ncu_decode.ncu-rep` beside this file, and
extracts the required metrics here. It refuses to run, with instructions, on a machine
whose driver restricts counters.

Then add the **measured-versus-theoretical occupancy** comparison against the theoretical
table in [analysis.md](analysis.md) — the specific quantity that table cannot supply.

## Release plan

This capture does not gate `v2.0.0`. Every kernel number in this repository is measured
and reproducible without it, and holding a working release for a rental that may not
materialise would serve nobody. It lands as a **documentation-only `v2.0.1`** cut at the
`v2.0.0` commit: no source changes, only this file, the occupancy comparison, and the two
`.ncu-rep` captures.

Until that happens, treat every claim in this repository about *which hardware unit is
saturated* as a model that has not been counter-validated.
